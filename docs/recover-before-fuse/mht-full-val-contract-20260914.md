## 2. 新增入口及完成条件

| 工具 | 职责 | 不代表什么 |
| --- | --- | --- |
| `prepare_mht_validation_campaign.py` | 核验全部缓存载荷、三个检查点和源码，保存三个固定任务的参数 | 不启动任务，不预留资源，不计算指标 |
| `audit_full_mht_validation.py` | 核验完整回执，执行只读身份账本审计并复算时延分位数 | 不重枚举真实场景全部候选，不证明完整后验质量或真实身份正确性 |
| `evaluate_mht_validation.py` | 先绑定完整审计，再在独立原生环境中读取冻结 GT 和计算 car 指标 | 不训练、不调参、不重写历史 ID，不作论文验收 |

完整审计入口额外要求：

- 确实完成 3,316 帧、21 序列，且存在 `full-validation-receipt.json`。
- 缓存、日程、模型清单、权重、完整配置、求解二进制及所有推断源码与冻结值相符。
- 预测、逐帧审计、计时、21 个 SQLite、序列提交头和最终回执逐项一致。
- 逐扫描重建原始因子、别名权重、合法父分支、同源同帧互斥和输出 ID 生命周期。
- 重算的逐帧时延分位数与回执一致；读取前后所有绑定文件摘要不变。

`audit_mht_validation.py` 仍是独立的开发重放审计入口，其
`full_validation_coverage_verified=false` 不变。原生评价拒绝用这类子集回执
代替完整审计。K=1、K=16 或其他预算不在本阶段的完整合同中；后续资源扫描须
另行预先固定，不能把某组 val 分数最高的配置回填为本阶段默认值。

完整原生评价继续使用冻结的 nuScenes、TrackEval 和 motmetrics 实现、严格
50 m ROI 和 car 映射。其指标、状态、时间定义与既有原生协议相同，输入选择
明确为 car-first-top64，不与旧 all-class-top64 表混比。AMOTP 以米报告、越低越好；
FP／FN／IDS 来自 nuScenes 标准工作点，IDF1 来自 TrackEval，不混用两套计数。

协议摘要为 `7a69b90abfd14afd33587036ef6d05b1121bcd6861af544afc326bbfa7b84cdd`。
它与 JPDA／PKF 协议仅方法标识不同；测试逐字段确认指标引擎、ROI、类别和其余
定义没有改变。共享 CPU 下的时延、RSS 和数据库大小仍是观察值，不证明等资源优势。
